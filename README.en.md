# Vigil ☉ — Ops Agent Harness

![Vigil](assets/banner.png)

> **Save triage time; keep decisions with humans.**
> AI does the cognitive work (discovery / diagnosis / remediation planning / evidence packaging); humans do the decision work (approve / veto / revise the plan).

Vigil is an **AI agent harness for ops scenarios**: when the agent works in real server environments, it both "remembers the whole platform" and "acts safely". Vigil is a complete fork of [Hermes Agent](https://github.com/juneauwang/vigil-agent-harness) (MIT License), keeping its mature agent core (terminal, tool calling, sessions, memory, plugins) while independently evolving a full production-ops capability set: the topology fact layer, the runbook procedure layer, the Permission Matrix, a controlled executor, and contract compilation.

## Why Vigil

Many small teams **have no dedicated ops staff**: servers are managed by developers on the side, no CMDB exists, no incident runbooks exist, and when something breaks at night you rely on memory. Vigil gives these teams the three things they lack most:

- **Memory** — a registry and relationship map of the platform (the topology table), so the agent doesn't "lose everything when the session changes"
- **Experience** — past incidents are consolidated into executable runbooks, so the next investigation doesn't start from scratch
- **Guardrails** — the Permission Matrix hard-blocks dangerous commands; deleting production by a slip of the hand goes from "relying on self-discipline" to "relying on mechanism"

If you have dedicated SREs, a complete CMDB, and a ticketing system — Vigil may be just a nice-to-have for you; if you are one person carrying a handful of servers — Vigil was built for you.

**Vigil's boundary (set 2026-08-24)**: AI automates the cognitive work, but decisions stay with humans — routine operations that have a runbook follow the pre-approved SOP (execute after approval); anomalies without a runbook notify a human to step in. Vigil does not do fully automatic remediation — AI replacing ops in decision-making is not the right shape yet.

## Core Features

| Layer | Carrier | Responsibility |
|---|---|---|
| **Fact layer** | Platform topology table (`topo_query` / `topo_update` / `topo-discover`) | Long-lived memory of the platform: entities, environments, dependencies, ownership. Generated by `topo-discover` automated topology discovery (SSH scans of docker/k8s/helm/ports + hardware probes); confirm the target's identity and environment before any ops action; cross-environment operations denied by default |
| **Procedure layer** | runbooks (`runbook_load` / `runbook_create` / the executor) | The only allowed "how to act": incident handling matches a runbook and executes its procedure; deployments advance through checklist stage gates; proven disposition flows consolidate into structured YAML, growing thicker with use. Supports nested orchestration (runbook calling runbook), scope inheritance, rollback linkage, and explicit variable passing |
| **Controlled executor** | 23-action command generation + script asset library | The execution engine generates commands uniformly (restart/backup/rollback/scale…), with variable substitution + target resolution + matrix approval gates + declarative `expect` verification + on_failure rollback. Long tasks proactively stream progress over SSE; same-name/same-target concurrency locks prevent duplicate execution |
| **Permission Matrix** | Operation matrix (`matrix.yaml` + `vigil matrix`) | action × environment → a three-state **execute / approve / reject** verdict, with no deny (a deny verdict invites LLM workarounds). The matrix is the sole adjudicator, covering all CLI/Web/scheduled/LLM paths; coverage gaps for high-risk actions show up on a dashboard |
| **Contract compilation** | YAML contract → LLM-generated thin wrapper (`vigil contract compile`) | Add tools for the LLM without writing code: author a YAML contract (params/returns/tests); the compile pipeline self-tests it in a sandbox and registers it as a tool after passing content approval. Credential discipline: contract parameters reject password/key-type parameters |
| **Audit layer** | Run trajectories (`vigil trajectory` / Web audit page) | Append-only event-level logs: who executed what command, when, and with what result; queryable, replayable, trimmable — the ledger for ops audit compliance |
| **Monitoring** | Health probes + PromQL queries + alert snapshots + alert-to-runbook disposition suggestions (Web monitoring page) | Health probes for topology entities (concurrent + cached, usable without Prometheus), PromQL-compatible queries + Alertmanager alert summaries; active alerts automatically match a disposition SOP — suggestions go to humans, and after human approval execution goes through the controlled execution chain |
| **Usage transparency** | Token usage panel + three-tier pricing sources | Current session / today / 30-day tokens and cost visible in real time; pricing precedence: manual override > online fetch > built-in fallback, with a zero-network-dependency floor |

## How It Differs from "Manual CMDB + RAG Docs"

The conventional approach (including quite a few AI ops products) is: **have the AI read documents (RAG) to understand the platform**. Vigil takes the opposite route: **have the AI fill in forms to consolidate platform facts**.

| | Vigil (form philosophy) | Manual CMDB + RAG |
|---|---|---|
| How platform facts enter the system | the agent fills forms, code generates YAML; the LLM never writes YAML syntax directly | humans enter CMDB records manually; the AI guesses by reading documents |
| Cost of consolidation | one proven run = a few clicks in a form, cost ≈ 0 | writing docs / entering records is expensive and easily backlogged |
| Trustworthiness of facts | topology table + validators as the safety net ("assume the LLM is a fool by default"), structured and verifiable | docs are maintained by humans; when they go stale, the AI can't tell |
| Judgment on the unknown | structured form constraints → validators reject; no making things up | when RAG retrieves nothing, the model improvises |

The core difference in one sentence: **Vigil trusts structure (verifiable execution specs); the RAG route trusts the model (prompt-guided, unverifiable).**

## How It Works

```text
               ┌─────────────────────────────────────┐
               │        Vigil session (per session)  │
               │                                     │
 injected at startup ──▶  TOPO section (topology table, layer 1)
               │        │                           │
 user instruction ────▶  topo_query confirms target identity/env ──▶ Permission Matrix
               │        │                    (action×env verdict)
               │   runbook_load matches a disposition procedure
               │        │                    execute / approve / deny
               │   executor (23 actions / nested runbooks)
               │        │                           │
 after execution ─────▶  topo_update refreshes facts + audit stamp
               │        │                           │
               │   experience consolidation: runbooks / contracts grow automatically
               └─────────────────────────────────────┘
```

Two iron rules hold throughout:

- **Confirm first, then act**: before any ops operation, check the topology to confirm the target; whichever target a command points at, that target's environment decides the verdict (a test-session operation on a prod node? the matrix blocks it outright)
- **Fail-closed by default**: when in doubt, refuse. The Permission Matrix is on by default; while the matrix is uninitialized, non-prod is lazily allowed and prod stays gated — better to wrongly block than to wrongly let through

### Usage-History-Driven Permission Self-Evolution (v0.1, command-level)

Beyond the operation matrix, Vigil consolidates **the read-only commands you approve repeatedly** into a command-level self-evolving allowlist (an original mechanism: not skills-style task experience, but command-level permission self-learning) — after the same command has been approved 3 times, the next invocation of the same shape executes directly without prompting; this shifts the model from "enumerated rules can never be complete" to "rule table as the base + usage history filling the gaps". Management entry points: `vigil approvals list` (full view, seed entries and self-evolved entries labeled separately) / `forget <template>` (revoke, back to prompting) / `export` (one-click backup export); data file `~/.vigil/approval_memory.yaml` (absent by default = empty allowlist + built-in read-only seed table as fallback).

Three red lines (welded shut, never relaxed):

- **Only user signals count, not execution success**: consolidation comes only from "user approved" events. Successful execution doesn't count; a command **rejected by the user even once → banned, never auto-consolidated again** (unbanning happens only via an explicit `forget`)
- **Consolidated templates, not raw strings**: `lscpu -e` / `sudo lscpu` normalize to `lscpu`; `cat /etc/hosts` normalizes to `cat`; shapes carrying dynamic arguments (URLs/IPs/value flags/operands/pipes/chained commands) and `rm`/`dd`/`mkfs`/redirection/`tee`/`shred`/`-rf` **never enter the allowlist**
- **Viewable / revocable / auditable**: every consolidated entry records its template, consolidation time, and source task; one command revokes it, and every consolidation/revocation/export is written to the trajectory

Security boundary: it applies only at the matrix `approve`/`unknown→approve` levels — the `{approve: required}` forced-human gate, the prod mutating hard gate, the missing-matrix deny, and the high-risk target-resolution deny are **never skipped by the allowlist**; unconditional layers such as tirith/dangerous-command checks still run on every command before execution. The built-in read-only seed table (lscpu/free/cat/ls/df/ps/... 18 commands total, a cold-start starting point, active by default) also fixes the misconfiguration where "bare read-only commands prompt for approval in prod"; unregistered read-only commands like `lsblk` still prompt first and self-evolve after 3 approvals. The v0.1 "don't ask again for these" opt-in is offered on the CLI approval surface (web/gateway approvals do not feed self-evolution signals — the conservative choice).

### Alert-to-Runbook Disposition Loop (batch87): alert → SOP suggestion → human confirms execution

Incoming active alerts are automatically matched to the most likely runbook (Alertmanager trigger-word exact hits > fuzzy scoring, reusing the same scorer as `runbook_load`): the result is a disposition suggestion (runbook / confidence / match rationale / runner-up SOP), each labeled with `matched_by` (trigger/fuzzy) and the hit keywords — transparent, so nothing misleads. The positioning is a **suggestion loop, not fully automatic remediation** — AI does discovery/diagnosis/suggestions, humans approve/veto: execution always goes through the existing runbook execution chain (operation matrix per-action adjudication + approval gates + audit); the matcher has zero bypass channels.

Entry points: `alert_triage` (agent tool; one call returns "the full active-alert picture + suggestions", with the tool description stating "suggestions only; execution requires user confirmation before calling runbook_execute"); the Web monitoring page's alert-row "suggest disposition" (match found → runbook name + confidence badge + view/confirm execution; no match → gray hint); CLI `vigil alerts` (list, `--json` for machine reading). Every triage call writes one lightweight audit entry to `runtime/alert_triage.jsonl` (reviewable via `vigil alerts history`) — the data source for dogfooding trigger words and match thresholds. A runbook's `triggers` field (including v0.2 structured `{alertname, severity}` exact matching) is what a hit is based on; this loop only matches and suggests — it does not change existing execution/adjudication semantics (matrix / approval gates / high-risk gates all as before).

## Quick Start

**Prerequisites**: Python 3.11+ (3.12 recommended), git

```bash
# 1. Install (creates the vigil command entry point)
pip install vigil-agent-harness

# 2. Enter Vigil directly — ops capabilities load by default (topology / runbooks /
#    Permission Matrix); a fresh default profile ships with ops config and a sample
#    topology, no initialization needed
vigil

# 3. Configure the model (e.g. DeepSeek) — add a model section to ~/.vigil/config.yaml,
#    and put the API key in .env in the same directory
```

> To manually rebuild the sample profile, use `vigil ops-init` (optional — still available for legacy users / self-hosted explicit rebuilds or migrations; no longer needed on first install).

After first entry, let Vigil learn your platform: **automated topology discovery** — tell it each machine's IP and SSH credentials, and it will SSH in and scan docker / k8s / systemd services / ports, generating an entity inventory for you to confirm before anything is written to disk:

```bash
vigil topo-discover          # guided: enter IPs + credentials → scan → human confirmation → written to topology.yaml
```

You can also edit the topology table by hand (`topology.yaml` + `entities/`, advanced usage). Then give it its first real job: **"check which entities in the topology have an expired last_verified"**.

## Web Console

Since v0.1.15 Vigil ships with a Web console (`vigil dashboard`, default http://127.0.0.1:9119):

- **Chat page** (`/chat`): talk to Vigil in the browser — streaming replies, collapsed tool-call display, multiple parallel sessions without interference; the token usage panel shows current-session/cumulative cost in real time
- **Topology map** (`/topology`): interactive topology graph (zoom/pan/click a node for a detail drawer), status coloring + liveness display; force-directed layout
- **Monitoring page** (`/monitoring`): service health table + alert list + trend sparklines
- **Global approval pop-up**: when the agent requests approval, a decision box (approve/reject/ignore) pops up on any page, with a live bell badge in the top bar; approving on the Web goes through the same approval flow as the CLI, and the prod mutating confirmation gate still intercepts
- **Runbook page**: execution entry + real-time progress panel (SSE streaming) + history + concurrency-lock indicator + high-risk-action coverage block
- Other pages: status / audit / matrix and more visualizations

```bash
vigil dashboard        # start the console; opens http://127.0.0.1:9119 in your browser
```

### Install from Source (developers / self-hosting)

Use this route when you want to modify code, run tests, or maintain a custom fork. One-shot script `setup-vigil.sh` (clone → install deps → initialize):

```bash
# Option A: already cloned the repo — run it in the repo root
git clone https://github.com/juneauwang/vigil-agent-harness.git
cd vigil-agent-harness
./setup-vigil.sh

# Option B: not cloned yet — one-shot remote (auto-clones to ~/.vigil/vigil-agent-harness)
bash <(curl -fsSL https://raw.githubusercontent.com/juneauwang/vigil-agent-harness/main/setup-vigil.sh)
```

The script creates `.venv`, installs dependencies, symlinks `vigil` into `~/.local/bin`, and asks whether to run `vigil ops-init`. Manual installation also works:

```bash
python3 -m venv .venv && .venv/bin/pip install -e .
.venv/bin/vigil ops-init          # or .venv/bin/python scripts/ops_init.py (same entry point)
.venv/bin/vigil -p ops
```

**Windows users**: native Windows support ships with the installer script `scripts/install.ps1` (PowerShell one-shot dependency install + `vigil` added to PATH). Inside WSL2, use the Linux path above directly.

## Security Model

| Layer | Mechanism | Notes |
|---|---|---|
| L1 | toolset trimming | sessions load a minimal toolset per role, shrinking the attack surface |
| L2 | static-rule hard gates | dangerous command patterns (rm -rf / drop table / delete namespace) blocked outright, 0 tokens |
| L3 | target-level Permission Matrix | the env of the action's target (a topology entity) decides the verdict: high-risk actions on prod are hard-rejected or require approval; the matrix has no deny — unknown actions default to allow with an audit record (a deny verdict invites LLM workarounds) |
| L4 | deployment checklist | production deployments must pass runbook stage gates: pre-flight checks → release → real verification → rollback plan |
| Credential discipline | credential injection chain | passwords/keys only flow through topology credentials + askpass injection, never into command strings/argv/logs; contract parameters reject credential-type parameters |

## FAQ

**Can't find the package on China mirrors?**
For freshly published packages, China mirrors (Aliyun/Tsinghua/USTC) sync with a lag (a few hours to a day). If you can't install it, switch to pypi.org directly:

```bash
pip install vigil-agent-harness -i https://pypi.org/simple/
# or: main package from pypi.org, dependencies from a China mirror (faster)
pip install vigil-agent-harness \
  --index-url https://pypi.org/simple/ \
  --extra-index-url https://mirrors.aliyun.com/pypi/simple/
```

**Getting "from versions: none"?**
Vigil requires **Python >= 3.11 and < 3.14**. On an older Python, pip reports `Could not find a version that satisfies the requirement ... (from versions: none)` — that's the version floor, not a network problem. Check `python3 --version` first, install Python 3.11+, then retry. uv gets you there in one shot:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
uv venv --python 3.12 .venv && source .venv/bin/activate
pip install vigil-agent-harness -i https://pypi.org/simple/
```

**Data directory**
Vigil's data directory is `~/.vigil` (override with `VIGIL_HOME`).
